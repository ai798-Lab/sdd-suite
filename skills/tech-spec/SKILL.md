# tech-spec · 技术 / 架构方案

把需求 + 设计落成可执行的技术蓝图。这是九个参考仓库共同的盲区,所以本 skill 以**原创 + SDD 方法论为主**,不照抄任何单一 repo。

> 位置(v0.3):**技术方案整体归这一步做**,不再分散在 spec 里。顺序是有道理的——spec 定了做什么、设计稿定了长什么样,这时才知道要几个接口、什么数据模型、哪些活是异步的。反过来先定技术栈再画页面,一定返工。
>
> spec 只留一句话级别的可行性粗判(挡住做不了的功能);从「靠什么实现」到「逐砖怎么砌」,全在这里。

## 启动

1. 读 `CONSTITUTION.md`。
2. **强制引用**:已批准的 `spec.md` 是必需输入;**设计稿强烈建议一起给**(页面状态与交互定了,接口契约才有依据)。无 spec.md 则停下,回 discover-spec;无设计稿可以做,但要在文首标注「接口契约基于假设的页面状态,设计稿出来后需复核」。
3. 产出落到 `docs/sdd/<slug>/` 下:`plan.md`、`data-model.md`、`contracts/`、`tasks.md`。文首写 `> source: spec.md`。

## Phase -1 gates(动手前先过门,借 SDD / spec-kit)

新增任何抽象层 / 框架 / 依赖前,在 plan.md 写书面 justification,过三问(详见 `references/phase-minus-1-gates.md`):

- **Simplicity**:能不能用更少的部件做到?
- **Anti-Abstraction**:这层抽象现在就需要,还是"以后可能用到"?(后者一律砍)
- **Integration-First**:能不能先打通端到端最薄一条,再谈优化?

没过门的抽象不许进 plan。

## 调研 pass:先搜再定,不凭记忆编(必过)

按 `references/tech-and-reuse.md` 的三条铁规做,这一段不许跳:

1. **不造轮子**:逐个功能问「有没有现成的能站上去」——开源项目 / 托管服务 / 平台原生能力。自研只留给核心差异化。
2. **真搜再写**:**真的去 WebSearch + GitHub 查当下情况**再写,给真实项目名 + 可点链接 + 选它的理由(star / 最近提交 / license / issue 活跃度)。**凭记忆、编一个不存在的库 = 假大空技术,打回。** 知识有截止,新东西尤其要查。
3. **服务要带价**:每个外部服务(auth / 支付 / 邮件 / 存储 / AI API)记下真实定价量级,并算两个数:零用户时月成本、一千日活时月成本。

产出落在 plan.md 的「复用清单」段:每条 = 功能 → 选用的项目或服务 → 链接 → 为什么选它 → 月成本量级。

## 技术选型矩阵

把关键技术决策列成矩阵:候选 × 评估维度(契合需求 / 团队熟悉度 / 运维成本 / 面向地区合规 / 商业模式约束)。每个决策落一条 **ADR**(Nygard 模板,见 `references/adr-template.md`):背景 / 决策 / 后果。决策点回指 spec 的 AC 与 design 的约束。

## 数据模型 + 接口契约

- `data-model.md`:实体 / 字段 / 关系,每个字段回指它服务的需求 AC。
- `contracts/`:接口契约(请求 / 响应 / 错误)。契约先行,实现在后。
- 铁律(borrow ecc):**不从现有代码反推业务真值**,未知标 `[ASSUMPTION]`。

## tasks.md:原子任务(借 superpowers writing-plans)

- 先 **map File Structure**:每文件单一职责,按职责而非技术分层拆。
- 再拆成 bite-sized 任务:单一动作、精确文件路径、明确验收(命令 + 预期输出)、零 placeholder。
- 可并行的标 `[P]`;能写测试的标 test-first。
- **spec coverage 自检**:反查每条 spec AC 是否都有对应 task。漏了就补。

## 方案自检:四维闸门(必过,见 `references/tech-eval-checklist.md`)

方案写完先自己过闸,任何一维不及格就回去改。判断基准是**十万用户之前**,不为还没到来的用量提前买单。

| 维度 | 自问 | 及格线 |
| --- | --- | --- |
| 上线门槛 | 从零到能访问要过几关?运维谁扛? | 全托管优先,推代码即部署;不碰服务器 / Nginx / 证书 |
| 成本曲线 | 零用户花多少?一千日活花多少?哪项会突然跳? | 起步走免费额度;按用量计费;盯住 AI API 与存储出口流量两个跳变项 |
| 体验与性能 | 首屏多久?长任务用户在看什么?接口几次往返? | 落地页静态化;长任务一律异步 + 进度反馈;一个动作一次往返 |
| 稳定性 | 上游挂了怎样?重复点怎样?数据会写坏吗? | 上游有适配层可切;扣费类操作原子化;失败可重试且不重复扣 |

外加一条经验判据:**能不能一个人维护**。每引入一个新服务就多一个要登录、要续费、要排障的地方;能一家托管平台解决的别拆成三家。

升级时机:**某一项开始疼了才升级**。任务频繁超时再把长任务挪去能跑长进程的平台;流量费肉疼再换出口免费的存储;连接被打满再上连接池。

## 评审与交接

- 自检覆盖率(borrow gstack):列一张"AC → task"对照,缺口显式标出。
- 四维闸门逐条写明结论(过 / 不过 + 理由),不许只写"已评估"。
- 可选:跨模型二次评审(换个模型对架构逐条挑刺)。
- **HARD-GATE**:plan + tasks 给用户批准,才移交实现。terminal state → 实现流程(executing / subagent-driven 等)。

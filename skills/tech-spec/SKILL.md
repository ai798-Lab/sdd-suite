# tech-spec · 技术方案与落地计划

把需求 + 设计落成可执行的技术蓝图,**并在同一步里排完期**。产出两类东西:技术方案(架构 / 选型 / 数据模型 / 契约)和落地计划(原子任务 + 并行编排)。中间夹两道用户确认门。

> 位置(v0.5):**技术方案与排期整体归这一步做**,不再分两趟。顺序是有道理的:spec 定了做什么、设计稿定了长什么样,这时才知道要几个接口、什么数据模型、哪些活是异步的;而任务怎么切、什么能并行,又完全由技术方案决定。拆成两个 skill 跑,中间要重读一遍上下文,还容易排出与方案对不上的任务。
>
> spec 只留一句话级别的可行性粗判(挡住做不了的功能);从「靠什么实现」到「逐砖怎么砌」到「谁先谁后」,全在这里。

## 启动

1. 读 `CONSTITUTION.md`。
2. **强制引用**:已批准的 `spec.md` 是必需输入;**设计稿强烈建议一起给**(页面状态与交互定了,接口契约才有依据)。无 spec.md 则停下,回 discover-spec;无设计稿可以做,但要在文首标注「接口契约基于假设的页面状态,设计稿出来后需复核」。
3. 产出落到 `docs/sdd/<slug>/`,文首写 `> source: spec.md`:

| 文件 | 装什么 |
| --- | --- |
| `plan.md` | 技术方案 + 执行编排:Phase -1 justification / 复用清单 / 选型矩阵与 ADR / 四维自检结论 / 批次编排与关键路径 / 每批的 worktree 执行清单 |
| `data-model.md` | 实体、字段、关系 |
| `contracts/` | 接口契约(请求 / 响应 / 错误) |
| `tasks.md` | 原子任务清单 |

## 职责边界:技术判断是你的活,不是用户的

**用户多数是小白,不懂技术,也不该懂。** 这个 skill 的价值就在于替他把技术上的事想完、查完、定完。

- **自主调研、自主选型、自主拍板**。每一个技术问题,你去搜、去比、去下结论,并写清为什么。
- **禁止把技术判断甩回给用户**。反例:「你想用 Postgres 还是 MongoDB?」「要不要上 Redis?」「你倾向哪个鉴权方案?」这些问题问出口就是失职。正例:「数据存 Postgres。你的数据有关系(一个用户对应多个订单),它最稳、托管最便宜、以后要搬也最容易。」
- **只有三类事可以问用户**,且必须先给推荐默认值 + 一句大白话理由:每月愿意花多少钱、数据放在谁家(合规 / 数据归属)、面向哪些地区和平台的硬限制。
- 用户在整个流程里只做两个动作:在 Gate 1 确认方向,在 Gate 2 确认计划。

## Phase -1 gates(动手前先过门,借 SDD / spec-kit)

新增任何抽象层 / 框架 / 依赖前,在 plan.md 写书面 justification,过三问(详见 `references/phase-minus-1-gates.md`):

- **Simplicity**:能不能用更少的部件做到?
- **Anti-Abstraction**:这层抽象现在就需要,还是「以后可能用到」?(后者一律砍)
- **Integration-First**:能不能先打通端到端最薄一条,再谈优化?

没过门的抽象不许进 plan。

## 调研 pass:先搜再定,不凭记忆编(必过,不许跳)

按 `references/tech-and-reuse.md` 的三条铁规做。这一段是本 skill 最费力也最值钱的部分,做法是**清单式的,逐个功能过**:

### 第一步 · 列功能清单

从 spec 的「页面与功能清单」抄出每一个功能点,列成一张表。**每一行都要有调研结论,一行都不许空着**。

### 第二步 · 每个功能至少两次真实检索

对每一行:

1. **GitHub 搜现成项目**(关键词 + 同义词各试一轮,按 star 与最近更新排),看有没有能直接站上去的开源项目 / 模板 / SDK。
2. **WebSearch 搜托管服务与当下现状**,看有没有买现成比自研划算的 API 服务,以及这个领域现在的主流做法是什么。

**凭记忆写、编一个不存在或已停更的库 = 假大空技术,直接打回重做。** 知识有截止时间,新东西尤其要查。

### 第三步 · 用固定判据筛,写出结论和理由

每个候选按这五条判,不合格的直接淘汰并写明淘汰理由:

| 判据 | 看什么 | 危险信号 |
| --- | --- | --- |
| 活着吗 | 最近一次提交距今多久 | 超过 12 个月没提交 |
| 有人管吗 | issue 有没有回复、PR 有没有被合、open issue 占比 | 提问全部无人应答、issue 堆积上千 |
| 能用吗 | star 量级 + 是否有真实使用者(文档 / 案例 / 下载量) | 只有 demo,没人在生产用 |
| 敢用吗 | license 是否允许商用(MIT / Apache 放心,AGPL 与自定义条款要单独说明) | license 会传染到你的代码 |
| 换得掉吗 | 抽掉它要改多少代码、有没有同类替代 | 深度绑定且全网只此一家 |

### 第四步 · 复用清单落盘

写进 plan.md 的「复用清单」段,每条五要素:**功能 → 选用的项目或服务 → 可点链接 → 为什么是它(引上表判据的真实数据)→ 月成本量级**。

- **不造轮子**:自研只留给「现成的都不满足」的核心差异化,并且要写明为什么现成的不够。
- **服务要带价**:每个外部服务(auth / 支付 / 邮件 / 存储 / AI API)记下真实定价,并算两个数:零用户时月成本、一千日活时月成本。

### 调研不合格的四个信号

出现任何一个,这一 pass 判不及格,回去重做:给的是技术名词没有项目名;有项目名没有链接;有链接但没有 star / 最近提交 / license 这类真实数据;把候选原样列给用户让他挑。

## 技术选型矩阵 + ADR

把关键技术决策列成矩阵:候选 × 评估维度(契合需求 / 团队熟悉度 / 运维成本 / 面向地区合规 / 商业模式约束)。每个决策落一条 **ADR**(Nygard 模板,见 `references/adr-template.md`):背景 / 决策 / 后果。决策点回指 spec 的 AC 与设计稿的约束。

矩阵是**给你自己推演用的**,不是给用户做选择题的界面。矩阵可以留在 plan.md 里备查,但 Gate 1 给用户看的是结论,不是矩阵。

## 数据模型 + 接口契约

- `data-model.md`:实体 / 字段 / 关系,每个字段回指它服务的需求 AC。
- `contracts/`:接口契约(请求 / 响应 / 错误)。契约先行,实现在后。
- 铁律(borrow ecc):**不从现有代码反推业务真值**,未知标 `[ASSUMPTION]`。

## 四维自检:本 skill 自己过的闸(必过)

**这是你替用户把的关,不是给用户的判断题。** 你自己逐维打分、自己修方案,用户只在 Gate 1 看到翻译成人话的结论。任何一维不及格就回去改,改到过为止,不许把不及格的方案端给用户让他决定。判断基准是**十万用户之前**,不为还没到来的用量提前买单(详见 `references/tech-eval-checklist.md`)。

| 维度 | 自问 | 及格线 |
| --- | --- | --- |
| 上线门槛 | 从零到能访问要过几关?运维谁扛? | 全托管优先,推代码即部署;不碰服务器 / Nginx / 证书 |
| 成本曲线 | 零用户花多少?一千日活花多少?哪项会突然跳? | 起步走免费额度;按用量计费;盯住 AI API 与存储出口流量两个跳变项 |
| 体验与性能 | 首屏多久?长任务用户在看什么?接口几次往返? | 落地页静态化;长任务一律异步 + 进度反馈;一个动作一次往返 |
| 稳定性 | 上游挂了怎样?重复点怎样?数据会写坏吗? | 上游有适配层可切;扣费类操作原子化;失败可重试且不重复扣 |

外加一条经验判据:**能不能一个人维护**。每引入一个新服务就多一个要登录、要续费、要排障的地方;能一家托管平台解决的别拆成三家。

升级时机:**某一项开始疼了才升级**。任务频繁超时再把长任务挪去能跑长进程的平台;流量费肉疼再换出口免费的存储;连接被打满再上连接池。

四维结论逐条写进 plan.md(过 / 不过 + 一句理由),不许只写「已评估」。

## HARD-GATE 1 · 技术方案确认(必停,说人话)

技术方案定稿、四维自检全过之后,**停下**,给用户一份大白话说明,只回答四个问题。**不许术语堆砌**:出现的每个技术名词,要么后面跟一句人话解释,要么删掉。

1. **这个方案解决什么问题**:用 spec 里的用户场景讲,一句话说清做出来是什么、用户怎么用、这套技术让它成立在哪。
2. **为什么这么选**:挑出会影响体验 / 花钱 / 以后能不能换的关键选择(建议不超过 5 条),每条一句大白话理由。示例写法:「登录用 Clerk 这个现成服务,不自己写。省掉密码找回、验证码、第三方登录这些坑,免费额度够你前一万个用户用,以后想换也只影响登录这一块。」
3. **大概花多少钱**:两档明确数字,零用户时月成本、一千日活时月成本。列清每一项花在哪,并点名哪一项会随用量突然跳。
4. **有什么风险和取舍**:诚实写 2 到 4 条。哪里为了省钱牺牲了什么、哪个上游挂了会影响什么、哪条以后长大了可能要返工、哪里还是假设(`[ASSUMPTION]`)没验证过。

用户在这一门只需要回答「行」或者「这条我不放心」。他不需要、也不应该在这里做技术选择。**用户确认之前,不许开始排期。** 用户指出不放心的地方,回去改方案,重过四维自检,再来一次 Gate 1。

## 排期第一步 · tasks.md(原子任务)

Gate 1 过了才做这一段。

先画 **File Structure map**:每文件单一职责,按职责 / feature 竖切,不按技术分层横切。这是后面能不能并行的物理前提。

再按 map 把每条功能 / AC 切成原子任务。一条合格任务同时满足四条:

- **单一动作**:动词开头(新增 / 改 / 删),做完一件事。
- **精确文件路径**:写 `src/auth.ts`,不写「鉴权模块」。
- **明确完成判据**:一条能跑的命令 + 预期输出(「错密码 `POST /login` 返回 401」),不是「功能正常」。
- **零 placeholder**:TBD / TODO / 待定 / 「加适当错误处理」全禁。

每条回指它服务的 spec AC(`-> AC-003`),并写清前置依赖(`<- T1`)。能写测试的标 test-first。一个新审阅者半天内做不完、review 不动的任务,太大,拆。

### 切分铁律:文件边界不重叠的任务才能并行

`[P]` 不是「看起来互不相干」就能标,判据只有一条:**两条任务改的文件集合完全不相交**。相交就串行,或者把任务重切到不相交为止。

除文件外,还有两种隐性依赖同样必须串行:B 要用 A 产出的数据或契约;B 要写进 A 才建好的表 / 才定义的类型。

### 反模式:这 6 种一看就是烂计划

1. 按技术分层拆(前端 / 后端 / 数据库各一条):文件全重叠,没法并行。要按职责竖切。
2. 任务带 placeholder(「实现登录(细节待定)」):待定就是没拆完。
3. 完成判据写「功能正常」:不可执行,必须是能跑出 0/1 的命令 + 预期。
4. 一个任务改 5 个以上文件:太大、无法独立 review。
5. 全标 `[P]` 但其实有依赖(接口没好,页面测不了)。
6. 漏集成冒烟任务:并行线合并后没人验端到端。

## 排期第二步 · plan.md(批次编排)

排成可执行的**批次**,不是一长条流水账:

- **批次**:批 1(无依赖的 `[P]` 地基)→ 批 2(依赖批 1)→ … → 集成冒烟收尾。
- **批次间是 gate**:批 1 全部审过、合进主干,才开批 2。
- **关键路径**:最长那条串行链,决定「最快多久跑完」。想提速,要么并行化,要么拆短关键路径上的任务。
- **每条 `[P]` 一棵 worktree**:树怎么开、谁先合,由下一节的执行清单编排,用户不碰 git 命令。

样例(spec 片段:邮箱密码登录,AC-001 错密码返回 401、AC-002 登录页 375px 不溢出、AC-003 接口文档含两种响应):

```
## tasks(单一动作 · 精确路径 · 可验证 · 文件不重叠)

- [ ] T1 [P] src/auth.ts   : 新增登录接口     -> AC-001
      判据:错密码 POST /login 返回 401,对的返回 token
- [ ] T2 [P] ui/login.css  : 新增登录页样式   -> AC-002
      判据:宽 375px 时按钮不溢出、占满整行
- [ ] T3 [P] docs/api.md   : 新增接口文档     -> AC-003
      判据:含 /login 请求体 + 401/200 两种响应
- [ ] T4     集成冒烟  <- T1,T2,T3           -> AC-all
      判据:合并后 npm run smoke 退出码为 0

## 执行计划

批次 1 [P 并行] : T1 / T2 / T3   文件不重叠,三棵 worktree 同时跑
批次 2 [串行]   : T4 集成冒烟     依赖批次 1 全绿
关键路径 : T1 -> T4
```

## 排期第三步 · 并行执行编排(worktree)

`tasks.md` 里已经有 `[P]` 标记和每条任务的文件集合,这正好是开 worktree 所需的全部输入。既然如此,**并行怎么跑也是你的活**:清单你排、树你开、活你派、合并你走流程。用户不该手敲 `git worktree add`,也不该自己记着哪棵树该先合。

### 第一步 · 平台能力自动探底(先探再排,不假设)

worktree 是 git 原生能力,理论上哪个平台都跑得起来;但**能不能真并行,取决于当前 coding agent 平台**。动手前先探三件事,探到什么写什么:

| 探什么 | 怎么探 | 探到了意味着 |
| --- | --- | --- |
| 原生 worktree / isolation | 当前 agent 有没有 worktree 隔离能力(如 Claude Code 的 worktree isolation)、有没有对应的入口或参数 | 直接用平台原生隔离,不用自己拼一串 git 命令 |
| 并发子 agent | 能不能一次派出多个子 agent 同时干活(有没有派子 agent 的工具,能不能一条消息里派多条) | 同一批次的多条线可以真并行 |
| 后台长任务 | 长时间命令能不能后台跑并回收结果 | 跑得慢的那条线不会堵住整批 |

再确认两个工程前提:当前目录是 git 仓库(`git rev-parse --git-dir`),工作区干净或已知残留是什么。不是 git 仓库,就没有 worktree 可言,直接走降级。

**三件事缺任何一件,降级为串行**,并在 plan.md 和 Gate 2 明确告诉用户:降级了、卡在哪一条、代价是什么。最坏的情况是嘴上排了三条并行线、实际一条条跑,用户还以为在并行。

### 第二步 · 每个可并行批次出一份 worktree 执行清单

写进 `plan.md`,一条并行线一条,六要素齐全:

| 要素 | 写什么 |
| --- | --- |
| worktree 目录 | `../<slug>-feat-auth`,与主仓同级,名字带 slug 防撞 |
| 分支名 | `feat/auth`,一条线一个分支,不共用 |
| 文件集合 | 这条线**允许改的全部文件路径**,与同批其他线零交集 |
| 任务清单 | 这条线包住的 task 编号与内容(`T1`) |
| 完成判据 | 合并前必须跑绿的命令 + 预期输出,直接抄 task 的判据 |
| 合并顺序 | 第几个合回主干,以及为什么(定契约与类型的先合,减少后面返工) |

样例(接上一节的 T1 / T2 / T3):

```
## 批次 1 · 并行执行清单(3 条线)

线 A  ../login-feat-auth  分支 feat/auth
      文件:src/auth.ts
      任务:T1 新增登录接口
      判据:错密码 POST /login 返回 401,对的返回 token
      合并:第 1 位(它定了响应结构,先合)

线 B  ../login-feat-ui    分支 feat/login-ui
      文件:ui/login.css
      任务:T2 新增登录页样式
      判据:宽 375px 时按钮不溢出、占满整行
      合并:第 2 位

线 C  ../login-docs       分支 docs/api
      文件:docs/api.md
      任务:T3 新增接口文档
      判据:含 /login 请求体 + 401/200 两种响应
      合并:第 3 位

批次 gate:三条全绿且全部合回主干,才开批次 2(T4 集成冒烟)。
```

### 第三步 · 按清单执行,用户不碰 git

清单是给 coding agent 执行的,不是给用户抄命令的。顺序固定六步:

1. **建树**:按清单逐条建 worktree 与分支;有原生 isolation 就用原生的。
2. **派活**:一条线派一个子 agent,只给它这条线的文件集合、任务、判据,不给整份 plan。**改动越出文件集合一律拒绝**,越界说明切分错了,回去重切,不许就地放行。
3. **验收**:每条线跑自己的完成判据,绿了才算完成;红的先修到绿,不带着红结果去合。
4. **合并**:按清单的合并顺序合回主干,每合一条重跑一次该条判据。
5. **收树**:合完删 worktree 与分支,别留一地残枝。
6. **过 gate**:整批合完跑集成冒烟,绿了才开下一批。

用户在这一整段里只做两件事:批准计划,以及冲突时拍板。

### 安全护栏(四条,破一条就停)

- **文件集合有交集的分支绝不并行**。这是切分铁律的回指:有交集不是「小心点就行」,是把这两条改回串行,或者把任务重切到零交集。
- **合并前必须跑该分支的完成判据**,没绿不许合。「看着做完了」不是判据。
- **合并冲突停下来问用户**,不自作主张解决。冲突本身说明文件边界当初切错了,值得让用户知道并决定:重切任务,还是接受某一边。
- **主干只进已验收的东西**。批次 gate 不可压缩,不许为赶进度先合后验。

### 降级路径:不并行,产出也一样

平台探不到并发能力,或者仓库不适合开 worktree(不是 git 仓库、有大量未提交改动、子模块 / LFS 情况复杂),就降级:

- 同一份 `tasks.md`,按依赖顺序**串行**跑,同批任务顺序执行。
- 判据、批次 gate、集成冒烟**一条不减**,产出完全一样,只是慢。
- 在 plan.md 与 Gate 2 里**明写降级原因与代价**(「当前平台不支持并发子 agent,三条线改顺序执行,总时长约为并行的三倍」)。

## 移交前自检(机器跑,别靠肉眼)

装了 `gen-plan` 就直接跑它带的校验脚本(plugin 装法在 `<插件根>/skills/gen-plan/validate-plan.mjs`):

```
node skills/gen-plan/validate-plan.mjs docs/sdd/<slug>/
```

它检查六件:① 每条 task 有文件路径 + 完成判据 + AC 回指 ② 无 placeholder ③ 同批 `[P]` 的文件不重叠 ④ plan 有批次 + 关键路径 ⑤ 有集成冒烟收尾 ⑥ 每条 spec AC 都被覆盖。任一不过 → NOT READY,回去重拆。

没装脚本就逐条肉眼过这六项,并贴一张「AC → task」对照表,缺口显式标出。

脚本不检查 worktree 执行清单,这一项自己过两条:每条线六要素齐全;同批各线的文件集合两两零交集(与第 ③ 项互为交叉验证,对不上说明清单和 tasks 脱节了)。

## HARD-GATE 2 · 计划确认(必停)

`tasks.md` + `plan.md` 出来、自检通过后,**停下**,给用户四句话摘要:

1. **总共几批、多少个任务、关键路径多长**:一句话说清「最快多久能跑完」。
2. **哪些能同时开工**:批次 1 的 `[P]` 任务各产出什么,用人话讲(「一条做登录接口、一条做登录页、一条写接口文档,三件事互不干扰,可以同时开」)。
3. **并行方案长什么样**:排了几条并行线、每条动哪些文件、平台探底结果支不支持真并行。降级为串行的话,在这里明说原因和代价。
4. **每一步做完能看到什么**:每批结束时用户能亲自验的东西是什么(能点开的页面 / 能跑的一条命令 / 能收到的一封邮件)。

用户在这一门确认两件事:**计划本身**,以及**并行方案**(几条线、每条动哪些文件)。两件都点头才移交实现,worktree 由你按执行清单自动建、自动派、自动合,用户不需要敲 git 命令。terminal state → 实现流程(executing / subagent-driven 等)。

## 可选:跨模型二次评审

移交前,可以换一个模型对架构与计划逐条挑刺,挑出的问题回灌本流程修改,而不是直接放行。

## 和 gen-plan 的关系

排期已经并进本 skill,正常流程不需要再单独跑 `gen-plan`。只有一种情况用它:方案没变、只想重新拆任务或调整批次(比如砍了范围、加了人手、某条并行线被证明切错了)。那时 `gen-plan` 只重写 `tasks.md` 与 `plan.md` 的执行计划段,不动本 skill 写下的技术方案段。

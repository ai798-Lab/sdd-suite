# 技术方案自检 · 四维闸门

判断基准:**十万用户之前**。目标是「稳妥、便宜、一个人能维护」,不是「架构优雅」。
每一维给结论(过 / 不过)+ 一句理由,不许只写「已评估」。

## 1 · 上线门槛

- 从零到用户能访问,要过几关?每一关谁来做?
- 要不要自己管服务器、Nginx、SSL 证书、进程守护?
- 部署是不是推代码就自动完成?

**及格线**:全托管平台优先,推代码即部署。任何需要 ssh 上机器的环节,对小白都是不及格。

## 2 · 成本曲线

- 零用户时月成本?一千日活时月成本?
- 哪一项会突然跳变?
- 计费是按用量还是按机器数?

**及格线**:起步能跑在免费额度内;按用量计费。两个必须盯住的跳变项:**AI API 调用费**(生成类产品的大头)、**存储出口流量费**(下载多的产品会被这一项打穿,选出口免费的对象存储)。

## 3 · 体验与性能

- 首屏多久出内容?落地页能不能静态化?
- 生成类长任务,用户等待时看到什么?
- 完成一个动作要几次接口往返?

**及格线**:落地页静态或服务端渲染,秒开;长任务一律异步 + 进度反馈,绝不让用户对着转圈干等;一个用户动作一次接口往返,别让前端串三四个请求拼数据。

## 4 · 稳定性

- 上游服务挂了或涨价,换供应商要改多少代码?
- 用户连点两次会不会扣两次费?
- 任务失败能不能重试?重试会不会重复扣?

**及格线**:上游有适配层,换供应商不动业务代码;扣费类操作在数据库层原子完成;失败可重试且幂等。

## 加试:能不能一个人维护

每引入一个新服务,就多一个要登录、要续费、要排障的地方。十万用户之前,服务数量越少越好。
能用一家托管平台解决的,别拆成三家。

## 什么时候该升级

**某一项开始疼了才升级**,不为还没到来的用户量提前买单:

- 任务频繁超时 → 把长任务挪到能跑长进程的平台
- 流量费开始肉疼 → 换出口免费的对象存储
- 数据库连接被打满 → 上连接池
- 单点故障影响收入 → 才谈冗余
